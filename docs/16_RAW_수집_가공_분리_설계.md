# 16. RAW 수집·가공 분리 설계

- 결정일: `2026-09-18`
- 상태: 구현 기준. AI 기반 구축·유지보수 / 코드 기반 반복 수집으로 확정. 실제 사이트·수집 코드·S3 연결은 미설정
- 현재 목표: URL 하나에서 공고와 첨부 원본을 수집해 S3에 보존하고, 동일 공고 재실행과 수정 공고를 구분한다.
- 문서 우선순위: 수집·증분 처리·구현 순서는 이 문서를 우선한다. Snowflake 시멘틱 레이어와 대화형 안내는 [15_대화형_정책자금_안내_전환계획.md](15_대화형_정책자금_안내_전환계획.md)를 유지한다.

## 1. 확정한 경계

수집 파이프라인의 완료 지점은 **S3 RAW 저장 완료**다. 지원대상·금리·한도·제외 조건을 해석하지 않으며, 정책자금 비즈니스 스키마나 Snowflake 연결 없이 독립 실행할 수 있어야 한다.

AI는 최초 사이트 탐색·코드 작성과 장애 분석·수정에 사용한다. 정기 수집은 검증된 Python Playwright 코드가 수행하며, 실행마다 LLM이 탐색하거나 코드를 다시 생성하지 않는다. 같은 코드를 반복 실행해도 사이트 변경·접근 제한·환경 차이로 실패할 수 있으므로 결과 검증과 장애 관측은 필수다.

두 번째 Agent는 저장 완료된 RAW 버전을 입력으로 받아 정책자금 정보를 정형화한다. PDF/HWP 파싱·OCR·LLM 추출·업무 검증은 이 단계의 책임이며, 실패해도 이미 보존한 원본에는 영향을 주지 않는다. 정책자금 스키마는 이 단계 구현 전에 설계한다.

그 이후 검증·승인된 데이터는 Snowflake에 게시하고, Semantic Views와 대화 Agent를 통해 기업 상태를 확인한 후 자금 후보를 안내한다. 별도 추천 REST API와 기업 프로필의 영구 저장은 여전히 초기 필수 범위가 아니다.

## 2. 구성별 책임

| 구성 | 맡는 일 | 맡지 않는 일 |
| --- | --- | --- |
| 개발·유지보수 Agent | 허용 URL 탐색, 구조 확인, 수집 코드·테스트 작성, 실패 원인 분석·수정 | 정기 수집의 필수 실행 주체, 정책 조건 해석, 무승인 운영 코드 교체 |
| Playwright MCP | 개발·진단 시 Agent에 브라우저 탐색 도구와 페이지 증거 제공 | 정기 수집 스케줄링, 자동 운영 배포, 데이터 품질 보증 |
| Python Playwright 수집 코드 | 매 실행 목록·상세·첨부 순회, 원본 확보, ID·해시 계산, 완전성 검사, S3 기록 | LLM 추정값으로 원문 대체, 실행 중 자체 코드 수정 |
| S3 RAW | 원본·메타데이터·개정본·수집 이력 보존 | 정책자금 비즈니스 필드 확정 |
| 가공 Agent와 검증 코드 | RAW 읽기, 파싱·OCR·정형화, 근거·업무 규칙 검증 | 수집 성공 여부나 원본 파일 변경 |
| Snowflake / Semantic Views | 검증·게시 데이터와 업무 의미 관리, 조회 | HTML/PDF/HWP 원본 저장소 대체 |
| Airflow | 검증된 작업 실행, 일정·재시도·상태 관리 | 사이트별 탐색 로직 내장 |

MCP는 도구 연결 규격이다. 개발자의 Codex에 Playwright MCP를 연결한 것과, 프로젝트의 Python Playwright 수집기를 설치·배포한 것은 다르다. 정상 수집은 LLM·MCP·Codex 데스크톱 앱 없이 실행 가능하게 한다. [MCP 공식 아키텍처](https://modelcontextprotocol.io/docs/learn/architecture)

기관마다 전체 크롤러를 복제하지 않는다. 시작 URL·탐색 범위·허용 도메인·한도는 설정으로 관리하고, 공통 방식으로 표현하기 어려운 목록·상세·첨부·페이지 이동 차이는 작은 기관별 어댑터로 관리한다. 다운로드·해시·저장·상태·재시도는 공통 모듈이 담당한다. 모든 사이트를 설정만으로 처리할 수 있다고 보장하지 않는다. 로그인·CAPTCHA·다운로드 제한·특수 뷰어 등은 실패 증거와 함께 운영 확인 대상으로 남긴다.

### 문서 기반 개발과 코드 기반 운영

- [GPT.md](../GPT.md): 공통 작업·보안·검증 지침
- [단일 기관 구현 지시서](tasks/01_collector_mvp.md): 입력·구현 범위·산출물·합격 기준
- [수집기 운영 안내](runbooks/collector.md): 검증된 실행 명령·결과 확인·실패 분석·복구

문서를 수정한다고 코드가 자동 변경되거나 수집이 시작되지는 않는다. AI에게 구현/수정을 명시적으로 요청하고 테스트한 버전을 사용한다. 장애는 일시적 오류·접근 제한·환경 문제·사이트 구조 변경으로 나누어 대응하며, AI 수정안을 운영 코드에 무승인 자동 적용하지 않는다. 별도 상시 코드 생성 Agent 구축은 첫 수집기의 선행조건이 아니다.

## 3. 수집 설정

`configs/sources/`에서 다음 운영 정보를 관리한다. URL·기관 목록은 사용자 확인 후 등록한다.

- 변경하지 않는 `source_id`, 표시용 기관명, 시작 URL
- 수집 대상 설명, 게시판 탐색 힌트, 허용 도메인·첨부 호스트
- 탐색 페이지·공고 수, 실행시간, 요청 간격, 재시도 한도
- 첫 실행의 과거 수집 범위, 매 실행 재확인 범위, 정기 전체 재점검 범위
- S3 버킷·리전·prefix와 RAW 메타데이터 버전

기관별 탐색 규칙과 어댑터의 선택 방법도 버전 관리한다. 설정에서 임의 코드나 셸 명령을 실행하지 않는다. 실제 실행 값은 `configs/sources/`를 기준으로 하고 작업 문서에 같은 값을 중복 관리하지 않는다. 개발·진단 Agent의 탐색·LLM 비용 한도는 정상 수집 설정과 분리한다.

공고 선택 기준은 확인된 게시판·카테고리·수집 범위를 바탕으로 코드/설정에 명시한다. 기업 자격조건을 해석해 공고를 누락시키지는 않는다. 경계가 모호하면 검토 대상 후보로 기록한다.

원문과 첨부에 포함된 지시는 데이터로만 취급한다. 브라우저·다운로더 모두 허용 URL과 리다이렉트 목적지를 검사하고, 내부망·클라우드 메타데이터 주소·임의 로컬 파일 접근을 차단한다. 브라우저 MCP 옵션만 보안 경계로 의존하지 않는다. [Playwright MCP 보안 안내](https://github.com/microsoft/playwright-mcp#security)

로그인이나 신청 제출, CAPTCHA 우회는 자동 수행 범위에 넣지 않는다. 사이트 이용 조건·자동 접근 정책을 확인하고 제한된 요청 속도를 지킨다.

## 4. 무엇을 원본으로 보존하는가

- `source.html`: 실제 HTML 응답을 확보할 수 있을 때 그 바이트를 보존한다. 확보하지 못했다면 있다고 표시하지 않는다.
- `rendered.html`: 자바스크립트 렌더링 후 DOM을 별도로 저장한다. HTTP 응답 HTML과 구분한다.
- `extracted_text.txt`: 페이지에서 기계적으로 추출한 전체 텍스트다. LLM 요약문으로 대체하지 않는다.
- `attachments/`: PDF/HWP/HWPX 등 첨부 원본을 바이트 그대로 저장한다. 수집 단계에서 문서 변환에 성공해야 할 필요는 없다.
- `metadata.json`: 실제 확보한 파일, 원본 위치, 수집 상태, 해시, 오류를 기록한다.

접근성 스냅샷만으로 전체 HTML 보존을 완료했다고 판단하지 않는다. Playwright MCP의 `browser_snapshot`은 접근성 스냅샷이므로 원문/DOM 파일 확보를 별도로 검증해야 한다. [Playwright MCP 도구 명세](https://github.com/microsoft/playwright-mcp#tools)

전체 페이지 수집은 실제 펼쳐 읽은 탭·접힌 본문·iframe 등 탐색 범위를 기록해야 한다. HTML 파일 하나만으로 이미지·외부 스크립트까지 완전한 웹 아카이브가 되는 것은 아니다. 첫 검증에서는 공고 본문과 첨부가 빠지지 않았는지를 확인한다.

첨부 다운로드는 브라우저 세션·쿠키가 필요한 경우 같은 인증 문맥에서 실행한다. 클릭/POST/blob 다운로드 등 지원 방식은 첫 사이트에서 확인한다. 파일 확장자만 믿지 않고 응답 상태, MIME, 파일 서명, 실제 크기와 해시를 검사하여 PDF 대신 로그인 HTML이 저장되는 문제를 구분한다. URL·원본 파일명·수집 방법도 보존하며, 저장 파일명은 경로 탈출과 이름 충돌을 방지한다.

## 5. 식별자와 RAW 메타데이터

비즈니스 스키마는 미정이어도 운영 메타데이터 계약은 첫 저장부터 필요하다.

| 항목 | 의미 |
| --- | --- |
| `metadata_schema_version` | RAW 메타데이터 형식 버전. 정책자금 스키마와 별개 |
| `source_id`, `institution_name` | 기관/게시판의 고정 ID와 표시명 |
| `announcement_id`, `identity_method` | 같은 공고를 계속 추적하는 ID와 생성 근거 |
| `source_record_id` | 사이트 게시물 번호가 있으면 보존 |
| `requested_url`, `final_url`, `canonical_url` | 요청·이동 후·동일 공고 판별용 URL |
| `title` | 페이지에서 확인한 제목. 확인 불가 시 null과 이유를 기록 |
| `run_id`, `snapshot_id` | 수집 실행 ID와 변경본/초기본의 불변 저장 ID |
| `collector_version`, `source_config_hash` | 실제 실행한 코드 버전과 비밀정보를 제외한 유효 설정의 해시. 변경 비교 해시와 구분 |
| `collected_at` | UTC 수집 시각. 원문 게시일과 구분 |
| `hash_strategy_version`, `content_hash` | 변경 비교 규칙 버전과 공고 내용/첨부 결합 해시 |
| `capture_status`, `errors` | 수집 완료·부분 성공·실패와 구조화된 사유 |
| `artifacts[]` | 파일별 ID·역할·원본 URL·원본 파일명·MIME·크기·SHA-256·S3 위치·수집 상태 |
| `previous_snapshot_id` | 직전 완료 버전. 최초는 null |

`announcement_id`는 `source_id + 게시물 고유키`를 우선 사용하고, 고유키가 없으면 보수적으로 정규화한 URL을 사용한다. 쿼리의 게시물 번호를 제거하지 않으며 제목이나 수집 시각을 ID로 쓰지 않는다. URL 별칭은 매핑으로 관리하고, 같은 공고인지 불확실하면 임의 병합하지 않는다.

`document_id`는 공고 안의 논리적인 본문·첨부 식별자다. 첨부가 교체되면 해당 파일의 해시가 달라진다. 안정적인 첨부 식별자를 확보하지 못하면 기존 파일과 무리하게 동일시하지 않고 파일 목록의 추가·삭제로 기록해도 된다.

`announcement_id`와 `content_hash`는 다른 개념이다. 공고가 수정되어도 ID는 유지하고 새 `snapshot_id`를 만든다. 전체 해시를 공고 ID로 사용하지 않는다.

## 6. S3 저장 구조와 완료 경계

기관명 대신 안정적인 `source_id`를 경로에 사용하고, 기관명은 메타데이터에 둔다. 경로는 운영 조회가 간단하도록 current/history 중심으로 유지한다. S3 버킷의 Versioning은 별도 보호수단이며, 애플리케이션 논리 버전은 아래 prefix로 관리한다.

```text
s3://<raw-bucket>/raw/<source_id>/records/<announcement_id>/current/
  source.html                   # 확보된 경우
  rendered.html                 # 렌더링 DOM
  extracted_text.txt
  attachments/<safe_filename>
  metadata.json                 # 완료 판정에 사용하는 manifest

s3://<raw-bucket>/raw/<source_id>/records/<announcement_id>/history/<snapshot_id>/
  ...                           # 변경 전 current 복사본

s3://<raw-bucket>/raw/<source_id>/runs/<run_id>/manifest.json
                                # 성공·변경 없음·부분 실패 기록
```

원본 파일들을 먼저 업로드하고, 필요한 파일의 업로드 및 무결성 확인이 끝나면 `capture_status=COMPLETE`인 manifest를 마지막에 기록한다. 가공 작업은 이 manifest가 확인된 버전만 입력으로 받는다. S3는 여러 key를 하나의 트랜잭션으로 갱신하지 않으므로 이 완료 경계를 애플리케이션이 관리한다. [S3 일관성 모델](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)

첨부 하나라도 실패하면 실행 결과를 `PARTIAL`로 기록하고 이미 받은 원본은 보존하되, 현재 완료 버전 포인터를 갱신하지 않는다. 부분 저장 버전을 정상 처리 대상으로 보내지 않는다. 재시도에서는 검증된 기존 업로드를 재사용할 수 있지만, 완료 manifest가 발행된 버전은 덮어쓰지 않는다.

초기에는 기관별 단일 실행으로 경합을 막는다. 상태에는 현재 완료 snapshot/hash와 manifest 위치, 최초 발견·최종 확인 시각을 둔다. 완료 manifest 저장 뒤 상태 갱신만 실패한 경우 재실행 시 복구하며 같은 완료본을 중복 발행하지 않는다. 멀티 워커 도입 전 조건부 상태 갱신이나 잠금으로 동시 쓰기를 통제한다. 버킷 Versioning은 추가 보호수단이며 위 논리 버전 관리를 대체하지 않는다.

버킷 공개 접근 차단·암호화·권한 분리를 적용한다. AWS 자격증명은 Agent 프롬프트나 소스에 넣지 않고 실행 프로세스의 자격증명 체계를 사용한다. 수집 프로세스는 지정 RAW prefix에 필요한 읽기/쓰기 권한만 사용하고, 가공 프로세스는 RAW 읽기와 별도 결과 위치 쓰기로 분리한다. 쿠키·인증 헤더·세션 파일은 RAW 공고 묶음이나 로그에 넣지 않는다.

## 7. 변경 감지와 증분 처리

해시 계산은 LLM이 아니라 코드가 수행한다.

1. 실제 저장한 모든 파일 바이트의 SHA-256을 계산한다. 무결성 확인용 원본 해시다.
2. 변경 비교용 사본에서는 결정론적이고 버전 관리되는 규칙만 적용한다. 수집 시각·세션 토큰 같은 잡음을 비교 입력에서 제외하되 금액·날짜·숫자·표·링크는 보존한다.
3. 제목·본문·의미 있는 링크/표와, 정렬된 첨부 목록의 논리 ID·이름·바이트 해시로 공고의 `content_hash`를 계산한다. `collected_at`, `run_id`, S3 경로는 넣지 않는다.
4. 동일 기관·공고의 직전 완료본과 같은 해시 규칙으로 비교한다. 규칙 버전이 바뀌면 원본 변경과 구분해 재계산/검토한다.

S3 ETag를 파일 SHA-256 대신 쓰지 않는다. ETag는 암호화·멀티파트 업로드 방식 등에 따라 단순 파일 해시와 같지 않을 수 있다. [S3 무결성 검사](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)

| 관측 결과 | 처리 |
| --- | --- |
| 처음 본 공고 | 원본과 최초 완료 버전 저장, 이후 가공 대상 등록 |
| 본문·첨부 동일 | 재확인 이력/시각만 추가, 같은 내용의 가공 작업 생성 안 함 |
| 본문 변경 | 새 RAW 버전 저장, 이후 가공 대상 등록 |
| 첨부 교체·추가·실제 삭제 | 본문이 같아도 새 RAW 버전 저장 |
| 첨부 다운로드 실패 | 삭제로 간주하지 않음. PARTIAL 기록 후 재시도/확인 |
| 목록 탐색 중 시간/페이지 한도 도달 | 범위 미완료로 기록, 전체 확인 성공으로 표시하지 않음 |
| 공고 접근 실패·목록에서 사라짐 | 삭제/사업 종료를 단정하지 않음. 이전 버전 보존, 확인 필요 표시 |
| A → B → A로 변경 | 직전 B와 다르므로 새 개정 이벤트로 기록. 과거 A와 같다는 이유로 변경을 누락하지 않음 |

바이트는 바뀌었으나 비교 규칙상 같다면 관측 로그에 그 차이를 남긴다. 달라진 원본은 관측 자료로 보존하고, 정형화 재실행만 생략한다. 검증되지 않은 본문 정규화로 변경을 숨기는 것보다 불필요한 재처리를 허용하는 편을 우선한다.

새 글만 보는 방식으로는 과거 공고의 수정을 감지할 수 없다. 증분은 처리량을 줄이는 원칙이지 과거 공고를 다시 방문하지 않는다는 뜻이 아니다. 초기에는 명시한 테스트 범위를 모두 재확인하고, 확대 시 활동 중 공고·최근 기간 재확인과 전체 재점검을 병행한다. 확인하지 않은 과거 범위는 최신성을 보장하지 않는다. HTTP ETag/Last-Modified는 요청 최적화 힌트이며 내용/첨부 확인을 무조건 대체하지 않는다.

### 조용한 누락과 실행 범위 검증

오류 없는 종료만으로 성공을 판정하지 않는다. 빈 목록 표시, 마지막 페이지 도달, 같은 페이지 반복, 본문 유무, 첨부 발견/저장 건수와 이전 실행 대비 급격한 차이를 확인한다. 신규 0건은 정상일 수 있으므로 고정 최소 건수만 강제하지 않고, 목록과 범위를 정상 확인했다는 근거를 남긴다. 판단이 불확실하면 검토 필요 또는 부분 실패로 기록한다.

공고별 COMPLETE와 전체 실행 범위 완료를 구분한다. 한 공고가 완료되어도 다른 페이지·첨부가 실패하면 실행 전체를 성공 처리하지 않는다. 확인하지 못한 범위의 진행 위치나 최종 확인 시각을 앞당기지 않으며, 실패 증거를 남기고 재실행 가능하게 한다.

## 8. 가공과 재처리

가공 상태는 RAW manifest와 분리된 실행 이력에 저장한다. 초기 RAW 수집에 Snowflake나 가공 작업 실행이 필요하지 않다. 후속 가공 시 COMPLETE manifest와 가공 이력을 대조해 미처리·변경본을 찾는다.

가공 작업의 식별 기준은 `announcement_id + snapshot_id + processing_version`이다. `processing_version`은 파서/OCR·모델·프롬프트·정책자금 스키마·검증 규칙 버전을 묶은 불변 실행 설정이다. 같은 조합의 성공 결과는 재사용하고, 실패 재시도는 attempt 이력으로 남긴다. 설정이 바뀌면 원본이 같아도 새 가공 작업으로 실행할 수 있어야 한다.

두 번째 Agent의 실패는 재수집 이유가 아니다. 원본이 충분하면 S3에서 다시 처리한다. 근거 누락·OCR 실패·스키마 위반·조건 충돌은 구분하고, 제한된 재시도 이후 검토 대상으로 남긴다. 추출 결과의 검증 PASS와 게시 승인은 별개이며, 대화 조회는 승인된 Snowflake 데이터만 사용한다.

정형 스키마는 원문의 비교 의미를 보존해야 한다. 예를 들어 `업력 7년 미만`을 `business_age_max: 7`만으로 저장하면 7년 포함 여부가 사라진다. 비교 연산자 `<`, 단위 `year`, 업력 계산 기준일·원문 근거를 함께 표현하는 계약을 가공 단계에서 설계한다.

## 9. 구현 순서와 완료 기준

### 1차: URL 하나의 수집 실증

1. 작업 지시서를 읽고 첫 게시판 URL·범위, 허용 도메인, S3 버킷·리전·접근 방식을 확인한다. 미정이면 공통 코드와 고정 자료 테스트까지만 진행한다.
2. 개발 Agent가 Playwright MCP로 실제 사이트를 확인하고, 공통 수집 모듈과 기관별 어댑터·테스트를 작성한다.
3. 검증된 코드를 LLM·MCP 없이 실행해 목록·상세·첨부를 순회한다. ID·RAW 메타데이터·해시·불변 경로는 첫 저장부터 적용한다.
4. 아래 테스트로 신규/변경/실패/재실행과 실제 S3 저장·재조회를 검증한다. Airflow와 Snowflake는 연결하지 않는다.

| 검증 | 합격 기준 |
| --- | --- |
| 실제 공고 한 건 | S3에서 본문과 첨부를 다시 받아 원본과 대조 가능 |
| PDF/HWP 다운로드 | 확장자가 아니라 실제 파일 내용과 크기·해시 확인 |
| 같은 공고 재실행 | 공고 ID 유지, 불필요한 가공 대상 없음, 재확인 기록 존재 |
| 본문 또는 첨부만 수정된 테스트 자료 | 새 버전과 직전 버전 연결, 과거 원본 유지 |
| 중간 다운로드/업로드 실패 | 부분 성공이 완료본으로 노출되지 않으며 재시도 가능 |
| COMPLETE 발행 후 상태 갱신 실패 | 재실행에서 완료본을 찾아 포인터 복구, 중복 발행 방지 |
| 실제 브라우저 탐색 범위 | 누락·차단·한도 도달을 성공과 구분하고 URL/오류/증거 기록 |
| 정상 코드 반복 실행 | LLM·MCP·Codex 앱 없이 headless 실행되고 코드 버전·설정 해시가 기록됨 |
| 조용한 누락 테스트 | 목록 선택 실패·페이지 반복·빈 본문·가짜 첨부 응답을 정상 신규 0건/완료와 구분 |

변경 테스트는 로컬 테스트 자료로 수행하고 실제 기관 공고를 수정하지 않는다. S3 연결 전 로컬 테스트가 통과해도 실제 S3 실증 완료로 간주하지 않는다.

### 2차 이후

- 기관 설정·필요한 어댑터를 추가해 다기관 탐색과 오래된 공고 수정 감지를 검증한다.
- 검증된 수집기를 Docker로 재현하고 EC2에서 제한된 수집·S3 저장·실패 복구를 확인한다. 개인 Mac의 경로·브라우저 프로필에 의존하지 않는다.
- 안정화된 수집 작업을 Airflow `policy_fund_ingestion`으로 호출한다. 주 1회 배치를 기본안으로 두되 요일·시각·시간대는 별도 확정한다.
- 정책자금 스키마를 설계하고 두 번째 Agent·검증·Snowflake 적재를 구현한다. 이후 `policy_fund_processing`으로 독립 운영한다.
- 승인 데이터의 Semantic Views와 기업 상태를 묻는 대화형 안내를 구현한다.
- `policy_fund_matching` 배치 DAG는 기업 프로필 저장·정기 재평가가 필요해질 때 도입한다. 초기 대화 요청별 매칭을 위해 세 번째 DAG가 반드시 필요한 것은 아니다.

Airflow는 완성된 코드 실행 진입점을 호출하는 역할만 가진다. Docker/Airflow 버전과 운영 연결은 해당 단계에서 검증하며 현재 빈 Compose 구성에 미리 서비스를 추가하지 않는다. MCP/Node.js 개발 도구와 Python 수집기 런타임을 구분하고, 배포에 실제 필요한 의존성·브라우저·OS 라이브러리를 버전 고정한다.

## 10. 현재 저장소와 다음 작업

현재는 프로젝트 전용 Python/uv 환경, 폴더 골격과 AI 작업·운영 문서가 준비된 상태다. 개발자의 Codex에 Playwright MCP가 연결되어 있어도 수집 코드·S3 업로드·AWS 인프라·Airflow DAG가 구현되었다는 뜻이 아니다.

- `workers/agent/`: 후속 탐색·진단 자동화 보조 공간. 정기 수집의 필수 의존성 아님
- `workers/collector/`: 원본 다운로드·무결성·변경 감지·S3 저장
- `workers/collector/adapters/`: 구현 시 추가할 기관별 탐색 차이
- `workers/extraction/`: 후속 RAW 파싱과 정책자금 추출
- `workers/validation/`: 후속 정형 데이터·업무 근거 검증
- `configs/sources/`: 기관별 설정
- `schemas/raw/`: 수집 구현 시 추가할 RAW 메타데이터 계약
- `schemas/policy_fund/v1.json`: 기존 정형화 계약 골격. RAW 수집의 필수 입력이 아님

실제 연결 전 필요한 정보는 첫 수집 URL·허용 범위·한도와 S3 버킷·리전·접근 방식이다. 개발은 현재 Codex와 Playwright MCP로 시작할 수 있으며, 별도의 상시 수집 LLM 서버를 먼저 만들 필요는 없다. 비밀키·쿠키·비밀번호는 문서나 대화에 직접 붙여 넣지 않는다.
