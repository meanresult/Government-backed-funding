# 11. 관리자 검토모델

정책자금 추천 서비스에서 운영 데이터 변경 초안을 관리자가 어떻게 검토하고 승인할지 정의한 문서입니다.

이 문서는 추천 규칙, 서류 안내, 자금 소개/신청방법 안내 링크, 자금 설명이 곧바로 사용자 추천 결과에 반영되지 않도록 `초안 -> 검토 -> 승인 -> 게시` 흐름을 고정하는 기준 문서입니다.

## 1. 검토모델의 목적

관리자 검토모델의 목적은 운영 데이터 변경이 사용자 추천 결과에 안전하게 반영되도록 통제하는 것이다.

- AI 파싱 결과나 운영자 직접 수정이 곧바로 게시되지 않게 한다.
- 변경 전/후 차이를 관리자에게 명확히 보여준다.
- 누가, 언제, 무엇을, 왜 승인하거나 반려했는지 남긴다.
- 문제가 생겼을 때 마지막 정상 게시 버전으로 되돌릴 수 있게 한다.
- 추천 API는 항상 게시 완료된 운영 버전만 읽도록 보장한다.

## 2. 적용 범위

### MVP 1차 필수

| 변경 대상 | 설명 |
| --- | --- |
| 추천 규칙 | 자금별 추천 조건, 세부유형 트리거, 신청 제한 규칙 |
| 서류 안내 규칙 | 기업 상태와 자금별 서류 묶음 조합 규칙 |
| 서류 가이드 | 문서명, 발급처, 발급방법, 외부 링크 |
| 자금 소개/신청방법 안내 링크 | 자금별 소개 URL, 신청방법 안내 URL, 링크 상태 |
| 자금 소개 | 결과 카드 요약, 상세보기 페이지 설명 구간 |

### 2차로 미뤄도 되는 범위

| 변경 대상 | 설명 |
| --- | --- |
| AI 문서 파싱 초안 | PDF/OCR/LLM 추출 결과로 만든 자동 변경 초안 |
| 알림 고도화 | 슬랙, 웹훅, 검토 기한 알림 |
| 자동 링크 검증 | 자금 소개/신청방법 안내 링크 주기적 헬스체크 |

MVP에서는 운영자가 직접 수정한 내용도 반드시 초안으로 저장한 뒤 검토/승인 과정을 거치는 것을 기본값으로 둔다. AI 파싱은 이후에 붙더라도 같은 검토모델로 합류하면 된다.

## 3. 역할과 권한

| 역할 | 할 수 있는 일 | 할 수 없는 일 |
| --- | --- | --- |
| `operator` 운영 담당자 | 문서 업로드, 초안 생성, 서류 가이드 수정 요청, 규칙 수정 요청 | 본인 초안 최종 승인, 게시, 롤백 |
| `reviewer` 검토/승인 담당자 | 초안 검토, 승인, 반려, 수정 요청, 게시 요청 | 관리자 계정 권한 변경 |
| `admin` 시스템 관리자 | 계정 권한 관리, 게시/롤백, 긴급 비활성화, 운영 설정 변경 | 감사 로그 삭제 |

실무 운영에서는 최소한 `작성자`와 `승인자`를 분리하는 편이 안전하다. 단, 데모나 1인 운영 MVP에서는 같은 사람이 두 역할을 가질 수 있으나, 로그에는 역할과 행위가 분리되어 남아야 한다.

## 4. 상태 모델

| 상태 | 의미 | 다음 상태 |
| --- | --- | --- |
| `draft` | 초안 생성됨. 아직 검토 대기열에 올리지 않음 | `in_review`, `rejected` |
| `in_review` | 검토 대기 또는 검토 중 | `approved`, `rejected` |
| `approved` | 검토자가 승인함. 아직 사용자 추천에 반영 전일 수 있음 | `published`, `rejected` |
| `rejected` | 반려됨. 반려 사유와 함께 보관 | `draft` |
| `published` | 실제 추천 서비스가 참조하는 운영 버전에 반영됨 | `rolled_back` |
| `rolled_back` | 이전 게시 버전으로 되돌림 | 종료 상태 |

MVP에서는 `approved`와 `published`를 한 번의 버튼으로 처리할 수 있다. 다만 DB와 로그에서는 승인 행위와 게시 행위를 분리해 남기는 편이 이후 운영에 유리하다.

## 5. 검토 대상 데이터 구조

관리자 검토 화면은 `draft_changes`, `review_queue_items`, `approval_logs`, `published_versions`를 중심으로 동작한다.

### 5.1 초안 변경안

| 항목 | 설명 |
| --- | --- |
| `target_domain` | 어떤 도메인을 바꾸는지. 예: `fund_rule`, `document_rule`, `document_guide`, `application_link`, `fund_detail` |
| `change_type` | `create`, `update`, `deactivate` |
| `before_snapshot` | 변경 전 데이터 |
| `after_snapshot` | 변경 후 데이터 |
| `diff_summary` | 관리자가 빠르게 읽을 변경 요약 |
| `confidence_score` | AI 추출 기반 초안인 경우 신뢰도 |
| `source_document_id` | 문서 기반 변경이면 원본 문서 연결 |
| `created_by` | 수동 생성자 또는 시스템 계정 |

### 5.2 검토 대기열

| 항목 | 설명 |
| --- | --- |
| `draft_change_id` | 검토할 초안 |
| `assigned_to` | 담당 검토자 |
| `review_status` | `waiting`, `reviewing`, `approved`, `rejected` |
| `reviewer_comment` | 승인/반려/수정 요청 의견 |
| `due_at` | 검토 희망 기한 |

### 5.3 승인 로그

| 항목 | 설명 |
| --- | --- |
| `target_domain` | 변경된 도메인 |
| `target_id` | 변경 대상 ID |
| `action` | `approve`, `reject`, `publish`, `rollback`, `manual_update` |
| `before_snapshot` | 처리 전 값 |
| `after_snapshot` | 처리 후 값 |
| `actor_id` | 처리 관리자 |
| `reason` | 처리 사유 |

## 6. 관리자 화면 구성

### 6.1 검토 대기열 목록

| 화면 항목 | 설명 |
| --- | --- |
| 상태 필터 | 전체, 대기, 검토중, 승인, 반려 |
| 변경 도메인 필터 | 추천 규칙, 서류 규칙, 서류 가이드, 자금 안내 링크, 자금 소개 |
| 자금명 필터 | 특정 자금만 보기 |
| 위험도 표시 | 사용자 추천 결과 영향이 큰 변경인지 표시 |
| 생성 경로 | 수동 수정, 문서 업로드, AI 추출 |
| 담당자 | 검토 담당자 |
| 생성일/기한 | 오래된 검토 건 우선 확인 |

### 6.2 검토 상세 화면

상세 화면은 변경 전/후 차이를 먼저 보여주는 것이 핵심이다.

| 구역 | 표시 내용 |
| --- | --- |
| 변경 요약 | `diff_summary`, 변경 도메인, 대상 자금, 변경 유형 |
| 원문 근거 | 문서 기반 초안이면 원본 파일명, 발췌문, 페이지 또는 위치 |
| Before / After | 변경 전 값과 변경 후 값을 나란히 표시 |
| 영향 범위 | 어떤 자금, 세부유형, 서류 묶음, API 응답에 영향을 주는지 |
| 검토 의견 | 승인/반려 사유 입력 |
| 액션 버튼 | 승인, 반려, 수정 후 승인, 보류 |

### 6.3 승인 전 체크리스트

| 체크 항목 | 설명 |
| --- | --- |
| 공식 근거 확인 | 공고문, 신청안내자료, 운영자 수동 근거가 있는지 확인 |
| 추천 결과 영향 확인 | 자금 추천 여부가 바뀌는지 확인 |
| 서류 안내 영향 확인 | 사용자에게 새로 노출되거나 사라지는 서류가 있는지 확인 |
| 신청 제한 문구 확인 | 체납, 제외업종, 권리침해 같은 민감 안내가 과도하지 않은지 확인 |
| 사용자 응답 노출 여부 확인 | 내부 점수, bundle_id, 관리자 로그가 사용자 응답에 노출되지 않는지 확인 |

## 7. 처리 흐름

### 7.1 운영자 직접 수정

1. 운영자가 관리자 화면에서 규칙, 서류 가이드, 자금 소개/신청방법 안내 링크, 자금 설명을 수정한다.
2. 시스템은 원본 데이터를 바로 덮어쓰지 않고 `draft_changes`에 저장한다.
3. 검토 대기열에 `review_queue_items`를 생성한다.
4. 검토자가 변경 전/후 차이와 영향 범위를 확인한다.
5. 승인하면 게시 버전에 반영하고 `approval_logs`를 남긴다.
6. 반려하면 반려 사유와 함께 초안을 보관한다.

### 7.2 문서 업로드 기반 변경

1. 운영자가 공고문 또는 신청안내자료를 업로드한다.
2. 시스템이 원본 문서를 저장하고 파싱 결과를 만든다.
3. 변경 감지 결과가 있으면 `draft_changes`를 생성한다.
4. AI가 만든 초안은 반드시 원문 근거와 신뢰도를 함께 보여준다.
5. 이후 검토/승인/게시 흐름은 직접 수정과 동일하게 처리한다.

### 7.3 게시와 롤백

1. 승인된 변경 묶음으로 새 게시 버전을 만든다.
2. 추천 API는 최신 `published` 버전만 읽는다.
3. 문제 발생 시 이전 정상 게시 버전으로 포인터를 되돌린다.
4. 특정 자금만 문제가 있으면 전체 롤백보다 `funds.is_active = false`로 임시 비활성화할 수 있다.

| 항목 | 이유 |
| --- | --- |

## 9. API 설계 메모

| Method | URL | 설명 |
| --- | --- | --- |
| `GET` | `/admin/review-queue` | 검토 대기열 목록 |
| `GET` | `/admin/review-queue/{item_id}` | 검토 상세 |
| `POST` | `/admin/review-queue/{item_id}/approve` | 승인 |
| `POST` | `/admin/review-queue/{item_id}/reject` | 반려 |
| `POST` | `/admin/published-versions` | 승인된 변경 묶음 게시 |
| `POST` | `/admin/published-versions/{version_id}/rollback` | 이전 버전으로 롤백 |

관리자 API는 모두 관리자 인증을 요구한다. 승인, 게시, 롤백 API는 최소 `reviewer` 이상 권한을 요구하고, 계정/권한 변경은 `admin`만 수행한다.

## 10. 테스트 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| 운영자가 서류 발급방법을 수정 | 바로 게시되지 않고 검토 대기열에 생성 |
| 검토자가 승인 | 새 게시 버전에 반영되고 승인 로그 생성 |
| 검토자가 반려 | 반려 사유 저장, 사용자 추천 결과 미변경 |
| AI 초안 신뢰도 낮음 | 검토 화면에서 낮은 신뢰도 표시 |
| 게시 후 추천 API 호출 | 새 게시 버전 기준으로 추천 결과 반환 |
| 롤백 실행 | 이전 게시 버전 기준으로 추천 결과 반환 |

## 11. 구현 주의사항

- 사용자 추천 API는 `draft`, `in_review`, `approved` 상태 데이터를 읽지 않는다.
- 운영자가 직접 수정해도 원본 운영 데이터를 즉시 업데이트하지 않는다.
- 승인 로그는 삭제하지 않는 것을 원칙으로 한다.
- 반려된 초안은 재검토 가능성을 위해 보관하되, 사용자 추천에는 영향을 주지 않는다.
- AI가 만든 초안은 반드시 원문 근거 또는 추출 근거를 함께 보여준다.
- 내부 `display_priority`, `bundle_id`, 관리자 검토 로그는 사용자 응답에 노출하지 않는다.
