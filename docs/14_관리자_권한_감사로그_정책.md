## 1. 정책의 목적

관리자 권한 감사로그 정책의 목적은 운영 데이터가 안전하게 수정되고, 문제가 생겼을 때 원인을 추적할 수 있게 하는 것이다.

- 누가 어떤 관리자 기능을 사용할 수 있는지 명확히 한다.
- 운영자가 만든 초안과 검토자가 승인한 변경을 분리한다.
- 게시와 롤백은 더 높은 권한에서만 수행하게 한다.
- 관리자 세션 토큰 원문을 저장하지 않는다.
- 누가, 언제, 무엇을, 왜 바꿨는지 감사로그로 남긴다.
- 감사로그는 삭제하지 않고 보관 정책에 따라 관리한다.

## 3. 관리자 역할

MVP의 관리자 역할은 세 단계로 시작한다.

| 역할 | 설명 | 대표 사용자 |
| --- | --- | --- |
| `operator` | 운영 데이터를 수정 요청하고 초안을 만드는 역할 | 운영 담당자, 상담 담당자 |
| `reviewer` | 초안을 검토하고 승인/반려하는 역할 | 검토 담당자, PM |
| `admin` | 게시, 롤백, 계정 권한을 관리하는 역할 | 시스템 관리자, 서비스 책임자 |

역할은 단순하게 시작하되, 코드와 DB에서는 역할값을 명확히 남긴다. 이후 조직이 커지면 `content_manager`, `rule_manager`, `auditor` 같은 세부 역할을 추가할 수 있다.

## 5. 승인 분리 원칙

실무 운영에서는 작성자와 승인자를 분리하는 것이 원칙이다.

| 원칙 | 설명 |
| --- | --- |
| 본인 초안 직접 승인 금지 | `operator`가 만든 초안은 다른 `reviewer` 또는 `admin`이 승인한다. |
| 1인 MVP 예외 | 데모나 1인 운영에서는 같은 사람이 작성과 승인을 할 수 있지만, 로그에는 작성 행위와 승인 행위를 분리해 남긴다. |
| 게시 권한 분리 | 승인과 게시를 같은 버튼으로 처리하더라도 내부 로그는 `approve`와 `publish`를 분리한다. |
| 긴급 변경 기록 | 긴급 비활성화나 긴급 롤백은 반드시 사유를 남긴다. |

MVP에서는 구현 복잡도를 줄이기 위해 `reviewer`가 승인과 게시를 동시에 수행할 수 있다. 다만 서비스가 실제 운영 단계로 넘어가면 `admin`만 게시할 수 있게 분리하는 편이 안전하다.

## 6. 세션 관리 정책

관리자 인증은 일반 사용자 로그인과 분리해서 관리한다.

| 항목 | 기준 |
| --- | --- |
| 세션 저장 | `admin_sessions`에 저장 |
| 토큰 저장 방식 | 세션 토큰 원문 저장 금지, hash만 저장 |
| 만료 시간 | MVP 기본 12시간 권장 |
| 로그아웃 | `revoked_at` 기록 |
| 권한 변경 시 | 해당 관리자의 기존 세션을 폐기하는 것을 권장 |
| 장기 미사용 계정 | 비활성화 또는 비밀번호 재설정 요구 |
| 실패 로그인 | MVP에서는 로그만 남기고, 2차에서 rate limit 적용 |

관리자 세션은 브라우저 저장소에 민감정보를 넣지 않는 방식으로 구현한다. 토큰이 필요한 경우 `HttpOnly`, `Secure`, `SameSite` 쿠키 사용을 우선 검토한다.

## 7. 감사로그 저장 기준

감사로그는 “누가 무엇을 바꿨는지”를 나중에 확인하기 위한 운영 안전장치다.

| 항목 | 설명 |
| --- | --- |
| `target_domain` | 변경된 도메인. 예: `fund_rule`, `document_rule`, `document_guide`, `application_link`, `fund_detail`, `admin_user` |
| `target_id` | 변경 대상 ID |
| `action` | `create_draft`, `approve`, `reject`, `publish`, `rollback`, `manual_update`, `role_change`, `login`, `logout` |
| `before_snapshot` | 변경 전 값 |
| `after_snapshot` | 변경 후 값 |
| `actor_id` | 행위를 수행한 관리자 |
| `acted_at` | 행위 시각 |
| `reason` | 변경 사유 또는 승인/반려 사유 |
| `source_document_id` | 문서 기반 변경이면 원본 문서 |
| `request_id` | API 요청 추적용 ID |

### 7.1 반드시 남길 로그

| 행위 | 로그 필요성 |
| --- | --- |
| 관리자 로그인/로그아웃 | 계정 보안 추적 |
| 관리자 권한 변경 | 권한 오남용 방지 |
| 초안 생성 | 운영 데이터 변경 시작점 추적 |
| 초안 승인/반려 | 검토 책임 추적 |
| 게시 | 사용자 추천 결과 변경 시점 추적 |
| 롤백 | 장애 또는 오류 대응 이력 추적 |
| 긴급 비활성화 | 사용자 노출 중단 사유 추적 |
| 문서 업로드/재처리 | 원본 근거 추적 |

### 7.2 로그에 저장하지 않을 값

| 저장 금지 값 | 이유 |
| --- | --- |
| 관리자 비밀번호 원문 | 보안 위험 |
| 세션 토큰 원문 | 탈취 위험 |
| OpenAI API Key, DB 비밀번호 등 환경변수 | 시스템 침해 위험 |
| 사용자의 신용점수 원점수 | 민감 금융정보 |
| 임대료, 보증금, 매출액 raw 값 | 추천 계산 외 장기 보관 불필요 |

필요하면 raw 값 대신 구간값, 마스킹값, 변경 요약만 남긴다.

## 8. 감사로그 보관 정책

| 로그 유형 | 보관 기준 |
| --- | --- |
| 승인/반려/게시/롤백 로그 | 장기 보관. 최소 서비스 운영 기간 동안 보관 권장 |
| 관리자 로그인/로그아웃 로그 | 1년 보관 후 보관 정책에 따라 정리 가능 |
| 실패 로그인 로그 | 6개월~1년 보관 권장 |
| 문서 업로드/파싱 로그 | 원본 문서 보관 기간과 맞춰 보관 |
| 추천 요청 로그 | 개인정보 raw 없이 90일 보관 후 집계값만 남기는 방식 권장 |

감사로그는 운영자가 임의 삭제하지 못하게 한다. 삭제가 필요한 경우 별도 보관 정책과 관리자 승인 이력을 남긴다.

## 9. 관리자 화면 표시 기준

### 9.1 권한에 따른 메뉴 노출

| 메뉴 | operator | reviewer | admin |
| --- | --- | --- | --- |
| 문서 업로드 | 노출 | 노출 | 노출 |
| 규칙/서류/CMS 수정 | 노출 | 노출 | 노출 |
| 검토 대기열 | 제한 노출 | 노출 | 노출 |
| 게시/롤백 | 숨김 | 요청 또는 제한 노출 | 노출 |
| 관리자 계정 관리 | 숨김 | 숨김 | 노출 |
| 감사로그 | 제한 노출 | 노출 | 노출 |

권한이 없는 버튼은 단순 비활성화보다 숨기는 편이 운영자 혼선을 줄인다. 단, 승인 요청 상태처럼 사용자가 알아야 하는 상태는 읽기 전용으로 보여줄 수 있다.

### 9.2 감사로그 화면 필터

감사로그 화면은 최소 아래 필터를 제공한다.

- 기간
- 관리자
- 변경 도메인
- 행위 유형
- 자금명
- 문서명
- 게시 버전
- 원본 문서

## 11. 테스트 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| `operator`가 초안 생성 | 초안 생성 가능, 검토 대기열 등록 |
| `operator`가 본인 초안 승인 시도 | 권한 오류 |
| `reviewer`가 초안 승인 | 승인 로그 생성 |
| `reviewer`가 게시 시도 | MVP 설정에 따라 허용 또는 권한 오류. 정책값으로 통제 |
| `admin`이 롤백 실행 | 롤백 로그 생성, 이전 게시 버전 적용 |
| 권한 변경 후 기존 세션 사용 | 세션 폐기 정책 적용 시 재로그인 요구 |
| 감사로그 삭제 시도 | 모든 역할에서 불가 |
| 세션 토큰 원문 조회 | DB에 원문이 없어 조회 불가 |

## 12. 구현 주의사항

- 권한 검사는 프론트가 아니라 백엔드에서 최종 수행한다.
- 관리자 세션 토큰은 원문 저장하지 않는다.
- 작성자와 승인자는 분리하는 것을 기본값으로 둔다.
- 승인과 게시를 한 버튼으로 묶더라도 로그는 분리한다.
- 감사로그는 삭제하지 않는다.
- 운영 데이터 변경 로그에는 변경 전/후 snapshot을 남긴다.
- 민감정보 raw 값은 감사로그에 남기지 않는다.
- 1인 MVP 예외를 허용하더라도 로그에는 예외 상황을 추적할 수 있게 남긴다.
