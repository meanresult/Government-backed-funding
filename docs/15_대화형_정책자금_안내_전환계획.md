# 15. 대화형 정책자금 안내 전환계획

- 결정일: `2026-09-17`, 수집·가공 분리 반영: `2026-09-18`
- 상태: 구현 방향 확정, 상세 스키마·도구 선정 전
- 적용 범위: AI/MCP로 구축한 코드 기반 S3 RAW 수집, 별도 Agent 정형화, Snowflake 정형 저장, 시멘틱 레이어, 대화형 자금 안내

## 1. 변경 결정과 문서 우선순위

별도 추천 API와 기업정보 입력 폼을 먼저 구현하던 계획을 변경한다. 먼저 정책자금 정보를 수집해 Snowflake에 정형 데이터로 저장하고 시멘틱 레이어를 정의한다. 이후 사용자가 프롬프트로 추천 자금을 물으면 AI가 부족한 기업 상태를 질문하고, 조회한 정책자금 조건을 근거로 후보와 준비사항을 안내한다.

대화형 안내 범위는 이 문서를 기준으로 하고, 수집·가공 분리와 구현 순서는 [16_RAW_수집_가공_분리_설계.md](16_RAW_수집_가공_분리_설계.md)를 우선한다. 기존 문서의 `챗봇은 MVP 이후`, `PostgreSQL 중심 저장`, `추천 API 우선 구현`, `자동 수집은 후순위`와 충돌하면 `15·16`과 `02·03·04`의 최신 변경 절을 우선한다. 기존 상세 문서는 삭제하지 않고 도메인·후속 웹서비스 설계 참고로 보존한다.

## 2. 구현 단계

| 단계 | 구현 내용 | 완료 기준 |
| --- | --- | --- |
| 1. RAW 수집 실증 | AI + Playwright MCP로 URL 하나의 수집기를 작성하고 검증된 코드로 HTML/본문/PDF/HWP 원본과 운영 메타데이터를 S3에 저장 | 원본 재확인, 동일/변경/첨부 실패 구분, 이전 버전 보존. 정상 수집은 LLM·MCP·정형화·Snowflake·Airflow 없이 동작 |
| 2. 수집 확장·배치 | 기관별 설정·어댑터 추가, 과거 공고 재확인, Docker/EC2 검증 뒤 Airflow 주간 실행 연결 | 실행 범위와 누락·실패가 관측되고 신규/변경본만 다음 단계 대상이 됨 |
| 3. 정형화·저장 | 정책자금 스키마 설계, 두 번째 Agent의 RAW 파싱·추출, 코드 검증, Snowflake 적재·승인 | 재수집 없이 재처리 가능하며 정형 결과에 원본 버전과 근거가 연결됨 |
| 4. 시멘틱 레이어 | 승인된 데이터 위에 Semantic Views 정의, 용어·관계·필터·집계 기준 관리 | 대표 조회 질문의 결과가 검증된 SQL 결과와 일치함 |
| 5. 대화형 안내 | 프롬프트 요청, 기업 상태 후속 질문, 조건 조회·비교, 근거 기반 답변 | 누락·모호한 입력을 확인하고 해당 기준일의 자금 후보와 추가 확인사항을 설명함 |
| 후속 | 전용 웹 UI, 추천 REST API, 관리자 CMS, 사용자 계정·이력 기능 | 실제 운영 필요에 따라 별도 범위 확정 |

초기 대화 검증은 선택한 Agent의 테스트 화면이나 최소 대화 클라이언트로 진행한다. Next.js 전체 화면, FastAPI 추천 엔드포인트, PostgreSQL 운영 DB는 1~5단계의 필수 선행 작업이 아니다. Agent와 데이터 조회 도구를 연결하는 기술적 호출은 필요하며, 이를 기존 `/api/recommendations` 구현과 구분한다.

## 3. 수집과 게시 흐름

1. 운영자가 사이트, 시작 URL, 수집 범위, 허용 도메인, 실행 한도와 RAW 메타데이터 버전을 설정한다. 정책자금 스키마는 아직 필요하지 않다.
2. 개발 Agent가 Playwright MCP로 공고·상세·첨부 구조를 확인하여 코드·테스트를 작성한다. 이후 정상 수집은 검증된 코드가 목록을 순회하고 HTML/DOM·본문·PDF/HWP 원본을 확보하며 ID·해시를 계산한다.
3. 원본·운영 메타데이터를 S3 RAW에 불변 버전으로 저장한다. 첨부까지 완료된 manifest를 기준으로 수집을 종료한다. 해석·Snowflake 적재·Airflow 연결은 이 성공 조건에 포함하지 않는다.
4. 별도 가공 작업에서 두 번째 Agent가 S3의 미처리/변경 완료본을 읽고, 이 단계에서 설계한 정책자금 스키마로 파싱·구조화 추출한다. 원문에서 확인되지 않는 값은 추정해 채우지 않는다.
5. 코드가 필수 필드·타입·단위·기간·중복·원문 근거를 검증한다. LLM의 자기평가 신뢰도만으로 PASS를 결정하지 않는다.
6. PASS 결과는 Snowflake의 검증된 대기 데이터에 적재한다. FAIL 결과는 원본과 실패 사유를 보존하고, 실패 종류에 따라 제한된 재추출·재검증 또는 수동 검토로 보낸다.
7. 검토자가 변경 근거를 확인해 승인하면 새 게시 버전으로 승격한다. 초기에는 관리 화면 없이도 승인자·승인 시각·변경 내용을 기록하는 운영 절차로 시작할 수 있다.
8. 시멘틱 레이어와 대화형 안내는 승인되어 게시된 데이터만 조회한다. 적재 PASS와 게시 승인은 서로 다른 상태다.

MCP는 도구 연결 규격이며 크롤러 자체가 아니다. Playwright MCP는 개발·진단에 사용하고 정상 수집은 Python Playwright 코드로 실행한다. 개발·유지보수 Agent는 수집기 작성과 장애 분석·수정에 관여하고, 별도의 두 번째 Agent가 RAW에서 정책 조건을 추출한다. 무결성·변경 감지·저장·업무 검증·게시는 제한된 권한의 코드와 운영 절차가 수행하도록 설계한다. 운영 코드 자동 수정·배포는 기본 범위가 아니다. [MCP 공식 아키텍처](https://modelcontextprotocol.io/docs/learn/architecture)

수집 목록 밖으로 확장하지 않도록 URL과 도구 사용 범위를 통제한다. 최대 탐색 수·실행시간·재시도 횟수와 요청 간격을 설정하고, 차단되거나 지원하지 않는 문서는 운영 확인 대상으로 남긴다. 외부 페이지 내용은 수집할 자료로 취급하며 Agent의 권한·설정을 바꾸는 지시로 사용하지 않는다.

## 4. Snowflake 저장 모델과 시멘틱 레이어

### 저장 역할

| 영역 | 역할 |
| --- | --- |
| S3 RAW | HTML/DOM·본문·PDF/HWP 원본, 수집 manifest와 버전 이력의 기준 저장소 |
| 수집 상태/실행 이력 | S3에서 현재 완료본·재확인·실패를 추적. 초기 수집은 Snowflake 없이 실행 |
| Snowflake 가공 이력 | 후속 가공의 S3 원본 참조, 추출 응답, 처리 버전·검증 이력. S3 RAW 원본을 대체하지 않음 |
| Snowflake STAGING | 정형 변환 및 검증을 통과했으나 게시 전인 데이터 |
| Snowflake CURATED | 승인된 정책자금 데이터, 개정 이력, 게시 버전 |
| Semantic Views | CURATED 기반 조회 관계·용어·차원·지표·기준일 의미 정의 |

영역명은 논리 설계이며 실제 데이터베이스/스키마 이름은 구현 시 확정한다. 가공 이력에 JSON을 보관하더라도 안내에 필요한 자금명, 기관, 지역, 기간, 금액, 자격 조건은 CURATED에서 타입과 관계가 명확한 정형 데이터로 관리한다.

Semantic View는 데이터를 다시 복사해 저장하는 테이블이 아니라 데이터의 업무 의미를 정의하는 Snowflake 객체다. 정의는 버전 관리하고 Snowflake에 배포한다. [Snowflake Semantic Views 공식 문서](https://docs.snowflake.com/en/user-guide/views-semantic/overview)

### 후속 정형화 단계의 데이터 계약

- 자금과 공고: 고정 자금 ID, 공고 ID, 개정 버전, 기관, 지원유형, 지역, 공식 URL
- 시점: 수집 시각, 확인 시각, 신청 시작/종료, 정책 적용 기간, 게시 버전. 날짜 미정·예산 소진 종료도 구분
- 지원 내용: 금액과 통화/단위, 업체당 한도와 사업 전체 예산의 구분, 금리의 고정/변동 여부와 기준일
- 자격 조건: 확인할 기업 필드, 비교 방식, 기준값과 단위, AND/OR 관계, 예외·제외 조건, 필수 증빙
- 서류: 조건별 필요 서류, 발급처, 공식 발급/안내 URL
- 근거와 품질: 원본 ID, 필드별 발췌 위치·문구, 추출/스키마 버전, 검증 결과, 승인 이력

같은 공고의 재수집과 실제 개정은 구분한다. 시멘틱 레이어의 기본 조회는 현재 게시 버전을 사용하고, 과거 비교는 질문의 기준일을 명시한다. 자금 수와 공고 수를 별개로 정의하고, 개정본 중복 집계나 지원 한도 합계를 전체 예산으로 표현하는 것을 방지한다.

현재 `schemas/policy_fund/v1.json`은 도메인 필드가 없는 골격이며 RAW 수집의 선행조건이 아니다. 첫 수집에서는 `16`의 RAW 운영 메타데이터만 정의하고, 두 번째 Agent 구현 전에 위 정책자금 항목의 실제 필드·비교 연산자·단위·필수 여부·누락값 정책을 확정한다. 기존 PostgreSQL DDL을 그대로 Snowflake에 적용하지 않는다.

## 5. 대화형 자금 안내

### 역할 분담

- 시멘틱 레이어: 기관·지역·업력·지원조건 등의 의미와 조회 관계를 제공한다.
- 대화 Agent: 사용자 의도 파악, 기업 상태 기억, 필요한 후속 질문, 조회 도구 선택, 결과 설명을 담당한다.
- 조건 확인: 승인된 조건 데이터와 조회 SQL 또는 작은 검증 함수로 비교한다. 별도 추천 REST API 없이 구현할 수 있다. 프롬프트나 모델의 사전지식에만 자격 판정을 맡기지 않는다.

Semantic View만 생성한다고 기업 상태를 묻는 대화나 자격 판정이 자동 완성되지는 않는다. 대화 상태와 질문·조회·비교·답변 지침을 별도로 구현하고 평가한다. Snowflake Cortex Agents를 대화 실행 환경의 우선 검토 대상으로 두되, 계정에서의 사용 가능 여부와 필요한 도구를 확인한 뒤 확정한다. [Cortex Agents 공식 문서](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents)

### 대화 순서

1. 사용자가 “우리 회사가 받을 수 있는 정책자금을 알려줘”라고 질문한다.
2. Agent는 기존 대화에서 확인된 기업 상태를 정리하고, 빠진 기본 정보를 짧게 나누어 질문한다. 이미 답한 항목은 반복해서 묻지 않는다.
3. 기본 상태로 후보를 좁힌 뒤, 후보별로 판단에 필요한 추가 조건만 질문한다.
4. 충분한 정보가 모이면 해당 게시 버전의 조건과 비교하고, 충족한 조건과 미확인 조건을 구분한다.
5. 사용자에게 자금 후보, 추천 근거, 추가 확인 조건, 서류, 공식 안내 링크, 데이터 기준일을 전달한다.
6. 사용자가 상태를 수정하면 해당 답변을 갱신하고 후보를 다시 조회·비교한다. 대화 중 게시 버전이 바뀌면 기준 변경을 알리고 재조회한다.

### 기업 상태 질문

기본 후보 탐색에는 업종, 사업장 지역, 사업자 유형, 개업 시점/업력, 매출 구간, 상시근로자 수, 자금 용도를 사용한다. 한 번에 전 항목을 요구하지 않고 필요한 항목부터 질문한다. 후보에 따라 체납 여부, 휴·폐업/재창업 여부, 신용 구간, 수출·혁신·피해 여부 등 추가 조건을 확인한다.

입력은 `확인됨`, `모름`, `답변하지 않음`, `아직 묻지 않음`을 구분한다. 누락을 `아니오`나 `0`으로 바꾸지 않는다. 매출 구간이 자격 기준의 경계를 걸치거나 업종이 모호하면 추가 질문 또는 확인 필요로 남긴다. 특정 자금에 영향을 주지 않는 민감 항목은 질문하지 않는다.

### 답변 기준

- 기업 상태가 부족하면 필요한 질문을 먼저 반환한다. 사용자가 답변을 생략하면 안내 가능한 범위와 미확인 조건을 함께 설명한다.
- 자금별로 확인된 충족 조건과 아직 확인하지 못한 조건을 구분한다. 조회된 후보를 최종 승인이나 대출 가능 확정으로 표현하지 않는다.
- 추천 이유와 조건에는 조회된 게시 데이터와 원문 근거를 연결한다. 모델이 금리·한도·접수 상태를 만들어내지 않는다.
- 조회 결과 없음은 확인한 데이터 범위와 기준일 안에서의 결과로 설명한다. 조회 장애와 실제 후보 없음은 다른 응답으로 처리한다.
- 오래된 데이터, 종료된 공고, 근거 부족은 표시하거나 확인 필요로 분리한다. 접수기간 안에 있다는 이유만으로 예산 잔여·실제 접수 가능을 단정하지 않는다.
- 서류와 링크는 후보에 연결된 승인 데이터에서 가져온다. 원문 검색/RAG는 필요할 때 추가하는 보조 기능이다.

## 6. 대화 상태와 운영 기록

기업 상태는 초기에는 대화 세션에서만 사용하고, 회사명·사업자등록번호·개인 신용점수 원값을 필수 입력으로 요구하지 않는다. 장기 기업 프로필 저장과 사용자 계정은 후속 범위다. 모델 제공자의 대화 저장 설정 및 로그 보관 정책도 세션 구현 시 확인한다.

문제 재현에는 실행 ID, 게시 버전, 시멘틱 정의 버전, 프롬프트/모델 버전, 조회 ID, 처리 결과를 사용한다. 원문 대화와 민감 입력을 운영 로그에 그대로 복사하지 않으며, SQL·도구 인자·오류 로그에 입력값이 들어가는 경우도 같은 정책을 적용한다.

수집용 S3 계정, RAW 읽기·가공/적재 계정, 대화 조회 계정의 권한을 구분한다. 대화 조회 계정은 게시 데이터 조회에 필요한 권한만 가지며, 초안·원본·운영 설정 변경 권한은 부여하지 않는다. 초기에도 실행시간·재시도·LLM 및 조회 비용을 관측한다.

## 7. 완료 검증 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| 동일 공고를 다시 수집 | 실행 이력은 남고 현재 공고가 중복 생성되지 않음 |
| 추출값에 근거가 없거나 필수값 누락 | 검증 실패/검토 대상으로 분리되고 게시되지 않음 |
| 검증 PASS지만 미승인 | 대화형 안내의 조회 대상에 포함되지 않음 |
| 기업 정보 없이 추천 요청 | 기본 기업 상태를 질문하며 구체적 자격 충족을 단정하지 않음 |
| 사용자가 이미 지역·업종을 답함 | 같은 내용을 다시 묻지 않고 부족한 조건을 질문함 |
| 사용자가 모름/생략으로 답함 | 해당 값을 추정하지 않고 확인 필요 조건으로 남김 |
| 경계값·AND/OR·예외 조건이 포함된 후보 | 검증한 SQL/조건 비교 결과와 일치함 |
| 기업 상태 수정 또는 게시 버전 변경 | 최신 상태와 명시된 게시 버전으로 다시 평가함 |
| 조회 결과 없음 또는 도구 장애 | 두 상황을 구분하고 근거 없는 자금을 생성하지 않음 |
| 자금 안내 답변 | 근거, 추가 확인사항, 공식 링크, 데이터 기준일을 제공함 |

대표 질문과 기대 조회 결과, 기업 상태별 추가 질문을 평가 자료로 관리한다. SQL 문장이 같은지가 아니라 반환한 후보·미확인 조건·근거가 맞는지 확인한다. 실제 구현 전 대표 사이트·공고와 검증 질문을 선정한다.

## 8. 남은 구현 결정

- 우선: 첫 수집 사이트·범위, S3 버킷/리전/접근 방식, RAW 메타데이터 계약
- 우선: 개발용 Playwright MCP 접근 확인과 수집기 실행 한도·검증 범위. 별도 상시 수집 LLM 서버는 초기 필수 아님
- 수집 실증 후: 다기관 재확인 범위와 Airflow 주간 실행 시각
- 가공 단계: 위 계약을 반영한 정책자금 스키마와 Snowflake 계정/리전/권한
- 대화 실행 환경과 최초 접근 화면, 세션 만료·보관 정책
- 초기 게시 승인 절차와 데이터 갱신 주기

이 결정들은 도구·운영 설정을 구체화하기 위한 항목이다. `S3 RAW 수집 → 다기관·배치 → 별도 정형화·Snowflake → 시멘틱 레이어 → 기업 상태를 묻는 대화형 안내`라는 구현 우선순위는 확정한다. 기업별 정기 매칭 DAG는 프로필 저장·재평가 요구가 생긴 후 선택적으로 도입한다.
