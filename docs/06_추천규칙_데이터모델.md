# 06. 추천규칙 데이터모델

정책자금 추천 서비스의 추천 엔진이 어떤 입력값을 받아 어떤 규칙으로 `추천`, `검토`, `불가`를 판단할지 정의하는 문서입니다. 본 문서는 현재 스프레드시트 기반 간이추천 로직을 서비스용 데이터 구조로 옮기는 것을 목표로 하며, 개발 관점에서 `입력 필드`, `추천 규칙`, `세부유형 후속 질문`, `서류 생성 규칙`의 단일 기준 문서로 사용합니다.

## 1. 문서 목적

이 문서는 아래 5가지를 데이터 구조로 고정하기 위해 작성한다.

- 어떤 입력 필드를 받을지
- 어떤 필드는 외부 데이터 소스를 통해 검색형으로 받을지
- 어떤 조건이면 공통 탈락인지
- 어떤 조건이면 자금별 추천 또는 추가 검토인지
- 어떤 조건이면 추가 서류와 추가 입력 섹션이 생성되는지

즉, 스프레드시트 수식에 들어 있던 판정 로직을 `코드 하드코딩`이 아니라 `운영 가능한 규칙 데이터` 형태로 정의하는 문서다.

## 2. 설계 원칙

- 추천 엔진은 입력값을 `정규화된 필드`로만 받는다.
- 공통 탈락 규칙과 자금별 추천 규칙은 분리한다.
- 서류 생성 규칙은 추천 규칙과 별도 도메인으로 관리한다.
- UI 확장 규칙은 추천 규칙과 별도로 관리한다.
- `공동대표`, `임차/전대`, `재도전`처럼 반복되거나 조건부로 열리는 입력은 `동적 섹션 규칙`으로 정의한다.
- 업종은 더 이상 단순 드롭다운 고정값이 아니라 `외부 API 기반 검색형 선택값`으로 다룬다.
- 추천 결과는 최소 `입력 필요`, `불가`, `추천`, `검토`, `해당없음`을 구분할 수 있어야 한다.

## 3. 추천 엔진 처리 흐름

추천 엔진은 아래 순서로 동작한다.

1. 입력값을 정규화한다.
2. UI 조건부 규칙을 평가해 추가 입력 섹션이 필요한지 판단한다.
3. 공통 탈락 규칙을 평가한다.
4. 공통 탈락이 없으면 자금별 1차 추천 규칙을 평가한다.
5. 세부유형이 필요한 자금은 후속 질문 그룹을 열어 추가 입력을 받는다.
6. 추가 입력을 반영해 자금 세부유형과 상태를 `추천`, `검토`, `해당없음`으로 확정한다.
7. 자금별 서류 규칙을 평가해 공통 서류와 조건부 서류를 만든다.
8. 추천 결과, 추가 확인사항, 제출서류를 함께 반환한다.

## 5. 업종 검색형 필드 모델

스프레드시트에서는 업종을 간이 드롭다운으로 처리했지만, 서비스에서는 검색형 필드로 바꾼다.

### 5.1 업종 필드 저장 구조

```json
{
  "field_id": "industry",
  "type": "remote_search_select",
  "required": true,
  "value_shape": {
    "industry_code": "string",
    "industry_name": "string",
    "industry_level": "major|middle|small",
    "standard_industry_name": "string",
    "is_excluded": "boolean",
    "source": "external_api|manual_override"
  }
}
```

### 5.2 업종 검색 UI 규칙

```json
{
  "field_id": "industry",
  "ui_behavior": {
    "search_mode": "autocomplete",
    "min_query_length": 1,
    "debounce_ms": 300,
    "max_results": 20,
    "display_template": "{industry_name} ({industry_code})",
    "allow_manual_override": true
  }
}
```

### 5.3 외부 API 연동 원칙

공식 소스 기준으로 바로 확인 가능한 것은 아래 2가지다.

- 소상공인시장진흥공단 `상가(상권)정보 API`
- 소상공인시장진흥공단 `상가(상권)정보 업종코드` 데이터

이 소스들은 업종 분류, 업종코드, 표준산업분류 기반 명칭을 제공한다. 다만 `실제 사업자등록상의 공식 업종 일치 여부`를 실시간 검증하는 API와는 성격이 다르다.

따라서 MVP에서는 아래 구조를 권장한다.

1. 업종 검색 자동완성은 외부 업종코드 데이터 기반으로 제공한다.
2. 검색 응답은 서비스 내부 캐시 테이블에 저장해 빠르게 조회한다.
3. 사업자번호를 추후 받는 단계에서는 국세청 사업자등록 상태조회 API로 휴폐업 여부 같은 별도 검증을 붙인다.

위 3번은 공식 소스와 현재 레포 요구사항을 합친 구현 추론이다. 즉, `업종 검색 API`와 `사업자 상태 검증 API`는 목적이 다르므로 분리하는 것이 더 안정적이다.

## 6. 공동대표 동적 확장 모델

`공동대표 여부 = 예`일 때는 단순 문구 노출이 아니라 반복 가능한 입력 섹션을 생성해야 한다.

### 6.1 기본 필드

```json
{
  "field_id": "has_joint_representative",
  "type": "boolean",
  "required": true
}
```

```json
{
  "field_id": "joint_representative_count",
  "type": "integer",
  "required": false,
  "default": 1,
  "min": 1,
  "max": 10
}
```

### 6.2 조건부 섹션 생성 규칙

```json
    "field": "has_joint_representative",
```


### 6.4 구현 해석

공동대표가 있을 때 UI는 아래처럼 동작하는 편이 좋다.

- `공동대표 여부 = 예` 선택
- `공동대표 수` 필드 노출
- 공동대표 수만큼 `공동대표 1`, `공동대표 2` 카드 또는 행을 자동 생성
- 각 카드마다 주거 형태, 임차 여부, 보증금/월세, 추가 증빙 상태를 입력

즉, `칸을 늘리는 방식`도 가능하지만 서비스 구현 관점에서는 `반복 그룹 카드`가 더 안정적이다.

## 7. 공통 탈락 규칙 스키마

공통 탈락 규칙은 자금별 규칙보다 먼저 평가한다.

```json
{
  "rule_id": "global-block-001",
  "rule_scope": "global",
  "rule_type": "blocking",
  "when": [
    {
      "field": "tax_delinquent",
      "operator": "equals",
      "value": true
    }
  ],
  "result": {
    "status": "ineligible",
    "message": "국세·지방세 체납은 해소 후 신청 가능합니다."
  }
}
```

공통 탈락 규칙 후보는 최소 아래를 포함한다.

- `tax_delinquent = true`
- `industry.is_excluded = true`
- `business_site_right_issue = true`
- 업종별 소상공인 상시근로자 기준 초과

## 8. 자금별 추천 규칙 스키마

자금별 추천 규칙은 공통 구조를 공유한다.

```json
{
  "fund_code": "innovation_growth",
  "fund_name": "혁신성장촉진자금",
  "version": "2026-05",
  "blocking_rules": [],
  "eligibility_mode": "variant_trigger",
  "eligibility_rules": [],
  "variant_rules": [],
  "display_priority": 80,
  "document_rule_refs": [],
  "notes": []
}
```

### 8.1 규칙 항목 공통 구조

```json
{
  "rule_id": "innovation-001",
  "rule_type": "variant_trigger",
  "field": "smart_tech_adoption",
  "operator": "equals",
  "value": true,
  "result_status": "recommended",
  "variant_code": "smart_tech",
  "variant_name": "스마트기술유형",
  "display_priority": 90,
  "message": "스마트기술 도입 기업"
}
```

`display_priority`는 추천 여부를 판단하는 점수가 아니라, 이미 추천 후보로 잡힌 자금이나 세부유형을 어떤 순서로 보여줄지 정하는 정렬값이다. 여러 조건을 더해서 다른 세부유형을 추천하는 방식으로 사용하지 않는다.

예를 들어 `수출 여부 = 예`와 `로컬크리에이터 = 예`가 함께 들어오면 `수출유형`, `로컬크리에이터유형`이 각각 매칭된다. 두 값을 더해 `스마트기술유형`을 추천하지 않는다.

### 8.2 상태값 정의

- `input_required`: 필수 입력이 부족함
- `ineligible`: 공통 탈락 또는 자금별 강한 불가
- `recommended`: 현재 조건으로 우선 추천
- `review_needed`: 추가 증빙 또는 상세 확인 필요
- `not_applicable`: 현재 입력 기준 직접 후보가 아님

### 8.3 혁신성장촉진자금 세부유형 트리거

혁신성장촉진자금은 상위 자금을 점수 합산으로 판정하지 않고, 세부유형별 조건이 직접 맞는지로 판단한다.

| 입력 조건 | 추천되는 세부유형 | result_status | display_priority | 해석 |
| --- | --- | --- | --- | --- |
| `smart_tech_adoption = true` | `smart_tech` 스마트기술유형 | `recommended` | `90` | 스마트기술 도입 조건이 직접 매칭됨 |
| `smart_factory = true` | `smart_factory` 스마트공장유형 | `recommended` | `90` | 스마트공장 조건이 직접 매칭됨 |
| `has_export_experience = true` | `export` 수출유형 | `recommended` | `80` | 수출 실적 조건이 직접 매칭됨 |
| `is_local_creator = true` | `local_creator` 로컬크리에이터유형 | `recommended` | `70` | 로컬크리에이터 조건이 직접 매칭됨 |
| `has_patent_or_ip = true` | 세부유형 미확정 | `review_needed` | `40` | 보조 혁신 신호로 보고 추가 확인 필요 |
| `has_esg_certification = true` | 세부유형 미확정 | `review_needed` | `40` | 보조 혁신 신호로 보고 추가 확인 필요 |

즉, 추천 여부는 `조건 직접 매칭`으로 정하고, `display_priority`는 여러 추천 후보가 동시에 나왔을 때 화면 정렬에만 사용한다.

### 8.4 상생성장지원자금 트리거

상생성장지원자금은 `온라인 판매 여부`만 확인되어도 1차 추천 카드로 노출한다. 다만 실제 신청 단계에서는 `TOPS/POST-TOPS 참여 필요` 안내를 반드시 함께 보여준다.

| 입력 조건 | 추천 자금 | result_status | display_priority | 사용자 안내 |
| --- | --- | --- | --- | --- |
| `sells_online = true` | 상생성장지원자금 | `recommended` | `60` | 온라인 판매 기업으로 확인되어 추천하되, TOPS/POST-TOPS 참여가 필요하다고 안내 |
| `platform_entry_or_tops = true` | 상생성장지원자금 | `recommended` | `80` | 플랫폼 입점, TOPS/POST-TOPS, 플랫폼 추천 확인자료 중 하나가 확인된 강한 추천 근거 |

`sells_online = true`와 `platform_entry_or_tops = true`가 동시에 들어오면 같은 자금을 중복 노출하지 않고, 추천 근거와 안내 문구만 합쳐서 보여준다.

## 10. 세부유형별 추가 입력 모델

기본 입력만으로도 1차 추천은 가능하지만, 일부 자금은 `세부유형 확정`과 `정확한 서류 추천`을 위해 후속 질문이 필요하다. 이 문서에서는 그 후속 질문 구조도 별도 문서로 분리하지 않고 함께 관리한다.

### 10.1 운영 원칙

- 공통 입력은 모든 사용자에게 먼저 받는다.
- 세부유형 질문은 모든 자금에 대해 일괄 노출하지 않고, `1차 추천 후보가 생긴 자금`에 대해서만 연다.
- 세부유형 질문의 목적은 `자금명 자체를 새로 추천`하는 것이 아니라, `세부유형 확정`, `추천 이유 보강`, `추가 서류 확정`이다.
- 세부유형 질문이 아직 없더라도 1차 추천 카드는 만들 수 있어야 한다.
- 세부유형 질문이 완료되면 `variant_code`, `variant_name`, `required_documents`, `detail_preview` 같은 결과가 더 정확해져야 한다.

### 10.6 구현 해석

- `06`의 공통 입력은 `1차 추천`용이다.
- `세부유형별 추가 입력`은 `정밀 추천`과 `맞춤 서류 확정`용이다.
- 따라서 프론트는 한 번에 모든 질문을 다 보여주기보다, `1차 추천 결과 후 보강 질문` 또는 `조건 충족 시 확장 질문` 방식으로 처리하는 것이 좋다.
- 후속 질문이 비어 있어도 상위 자금 카드는 노출할 수 있지만, 세부유형명과 일부 추가 서류는 비워둘 수 있다.
- 이 후속 질문 구조는 별도 문서가 아니라 본 문서의 일부로 유지하는 편이 규칙 변경 관리에 더 유리하다.

이 문서에서는 추천 엔진이 최소 아래 개념을 계산할 수 있으면 충분하다.

## 부록 B. 구현 메모

### B.1 업종 검색 구현 권장 방식

- 실시간 타이핑마다 외부 API를 직접 치기보다 내부 캐시 테이블을 두는 편이 낫다.
- 초기 적재는 외부 업종코드 데이터로 수행한다.
- 관리자 또는 배치 작업으로 업종코드 동기화를 수행한다.
- 검색 결과에는 최소 `업종명`, `업종코드`, `표준산업분류명`, `제외업종 여부`가 있어야 한다.

### B.2 공동대표 UI 구현 권장 방식

- `공동대표 여부 = 예`일 때 `공동대표 수`를 먼저 묻는다.
- 그 다음 수만큼 카드형 반복 섹션을 생성한다.
- 각 카드에 대해 주거형태, 임차 여부, 보증금/월세, 추가 서류 플래그를 받는다.
- 추천 엔진은 `joint_representatives[]` 배열을 순회하면서 서류 규칙을 적용한다.

### B.3 서류안내 UI 구현 권장 방식

- 결과 화면은 `신청 시 작성/동의`, `자동확인`, `기본 제출 권장`, `심사 후 또는 필요 시 제출` 4개 블록으로 나누는 편이 읽기 쉽다.
- `사업장 임대차계약서`는 항상 `주된 사업장 기준` 문구를 함께 노출한다.
- 거래내역 자료는 원칙적으로 심사 보강자료로 두되, 상담 초기에 미리 받아도 되는 것으로 분류한다.
- `법인 인감증명서`처럼 기관별 발급 경로 확인이 필요한 서류는 운영 메모를 함께 둔다.

### B.4 제외업종 처리

- 업종 검색 결과 단계에서 `is_excluded = true`를 함께 계산해 저장한다.
- 추천 엔진은 업종명을 텍스트 비교하지 않고 `industry.is_excluded`만 본다.
- 운영자가 예외 업종 매핑을 수동 조정할 수 있는 관리자 override 테이블이 있으면 더 안전하다.
