## 1. 현재 사용할 수 있는 것과 없는 것

| 항목 | 현재 상태 |
| --- | --- |
| 로컬 Python·uv | 프로젝트 전용 환경 준비. 아래 확인 명령 사용 가능 |
| 개발용 Playwright MCP | 개발자 Codex에서 별도 설정. 프로젝트/EC2 설치와 구분 |
| SEMAS 기관 설정·RAW 스키마·수집 코드 | 구현됨 |
| 실제 사이트·S3 저장 실증 | 미실행 |
| Docker 서비스·EC2·Airflow | 미구현·미배포 |

프로젝트 루트의 환경 확인 명령:

```bash
./uv --version
./uv run python --version
```

설치·동기화는 [README](../../README.md)의 `프로젝트 전용 Python 환경` 절을 따른다. `docker-compose.yml`은 빈 골격이므로 현재 `docker compose up`만으로 수집기가 시작되지 않는다.

### 현재 검증된 실행 명령

`python -m workers.collector`는 구현된 실행 진입점이다. `--storage s3`는 AWS 자격증명과 버킷 권한을 확인한 뒤 별도로 실증한다.

| 작업 | 검증된 명령 | 상태 |
| --- | --- | --- |
| 고정 자료·회귀 테스트 | `./.venv/bin/python -m unittest discover -s tests -v` | 통과: 5건 |
| 기관 설정 검증 | 설정 로더 실행 | 통과: `semas_ols_notice` |
| 제한된 로컬 수집 | `./.venv/bin/python -m workers.collector --source semas_ols_notice --storage local --max-notices 1` | 통과: 공고 407과 PDF 저장 |
| 승인된 S3 수집 | 미정 | 대상·권한 확정 및 실증 후 기록 |
| 실패 작업 재시도 | 미정 | 상태 복구 검증 후 기록 |
| Docker 실행 | 미정 | 로컬 실증 이후 별도 구성 |

## 2. 실행 전 확인

1. 구현 지시서의 완료/미완료 항목과 마지막 실사이트 검증 기록을 확인한다.
2. `configs/sources/<source_id>.yaml`의 기관·URL·허용 도메인·수집 범위·한도·저장 대상을 확인한다. 문서의 예시 URL을 운영 설정으로 사용하지 않는다.
3. 승인된 코드 버전과 잠금 파일을 사용한다. 실행마다 패키지를 `latest`로 바꾸지 않는다.
4. 브라우저·OS 의존성, headless 실행, 다운로드 경로의 용량과 쓰기 권한을 확인한다.
5. S3 대상 prefix와 자격증명 제공 방식·최소 권한을 확인한다. 키를 터미널 출력·문서·프롬프트로 복사하지 않는다.
6. 해당 기관의 다른 수집 실행이 진행 중이지 않은지 확인한다. 상태 경합을 피한다.
7. 실행 범위·예상 요청량이 승인된 한도를 넘지 않도록 확인한다. 정해지지 않은 전체 사이트 수집을 시작하지 않는다.

## 3. 결과와 성공 판정

결과는 `run_id`로 찾는다. 구현 시 실제 로컬 경로와 S3 prefix를 아래 기록표에 연결한다.

- 실행 이력: `runs/<run_id>/`에 범위, 코드 버전, 설정 해시, 시작/종료 UTC, 건수, 실패 원인, 증거 위치를 기록한다.
- RAW current: `raw/semas_ols_notice/records/announcement_<id>/current/`에 원본·본문·첨부·metadata를 보존한다.
- RAW history: `raw/semas_ols_notice/records/announcement_<id>/history/<snapshot_id>/`에 변경 전 current를 보존한다.
- 실행 이력: `raw/semas_ols_notice/runs/<run_id>/manifest.json`에 범위·건수·오류를 기록한다.

위 경로는 저장 계약이며 생성 완료된 자원을 의미하지 않는다. 상세 객체 규칙은 `16` 문서를 따른다.

| 관측 결과 | 판정·확인 |
| --- | --- |
| 신규/변경 공고의 필수 파일과 COMPLETE manifest 확인 | 해당 공고 수집 완료 |
| 내용·첨부 동일, 재확인 이력 있음 | 정상 변경 없음. 새 내용 버전이 반드시 생길 필요 없음 |
| 신규 공고 0건 | 목록·순회·범위 확인 근거가 있어야 정상. 단순 빈 결과만으로 성공 처리 금지 |
| 일부 첨부·페이지·업로드 실패 또는 한도 도달 | 실행 범위 미완료. 전체 성공으로 표시하지 않음 |
| COMPLETE manifest 뒤 상태 갱신 실패 | 복구 필요. 원본을 다시 덮어쓰지 않음 |

공고 하나의 완료와 전체 실행 범위의 완료를 구분한다. 성공한 공고는 보존하되, 실패한 부분이 있으면 전체 범위 확인 시각/진행 위치를 완료된 것처럼 갱신하지 않는다. 종료 코드도 이를 반영하며 실제 숫자 매핑은 구현 후 기록한다.

S3 실증에서는 저장된 파일을 다시 읽어 원본·해시를 대조한다. 다운로드 버튼 클릭, 로그의 `success` 문구, 로컬 파일 생성만으로 S3 저장 완료를 선언하지 않는다. 제한 옵션(`--max-pages`, `--max-notices`)을 사용한 실행은 범위가 잘린 `PARTIAL` 실행이므로 운영 성공으로 보지 않는다.

## 4. 장애 분류와 초기 대응

| 증상 | 먼저 확인할 것 | 대응 |
| --- | --- | --- |
| 네트워크 시간 초과·일시적 서버 오류 | 응답 상태·현재 URL·재시도 이력 | 제한된 횟수와 대기 간격으로 재시도 |
| 버튼/목록/본문을 찾지 못함 | 저장된 HTML·화면·추적 자료, 현재 DOM과 선택자 | 구조 변경 여부 확인 후 어댑터 수정·회귀 테스트 |
| 신규 0건·수집량 급감·같은 페이지 반복 | 빈 목록 표시·다음 페이지 이동·설정 범위·이전 실행 | 정상 빈 결과와 조용한 누락 구분. 불확실하면 확인 필요 |
| PDF/HWP 대신 HTML·빈 파일 저장 | MIME·파일 서명·크기·로그인 화면 여부 | 정상 첨부로 처리하지 않고 PARTIAL로 기록 |
| 로그인·CAPTCHA·접근 차단 | 리다이렉트·응답·사이트 정책 | 자동 우회하지 않고 운영자 확인 |
| S3 권한·대상 오류 | 승인된 대상·자격증명 유효성·권한 | 잘못된 대상에 대체 저장하지 않음. 권한 변경은 승인 후 처리 |
| 브라우저 실행 실패 | 브라우저 버전·OS 라이브러리·메모리·디스크 | 환경 문제와 사이트 코드 문제를 분리 |
| 부분 업로드·상태 갱신 실패 | 파일·manifest·현재 버전 포인터 | 검증된 상태 복구 절차로 재실행 |

모든 실패를 웹사이트 요소 변경으로 단정하지 않는다. 무한 재시도, 무조건적 대기시간 증가, 선택자 추측 수정은 기본 대응이 아니다.

## 5. AI 분석·수정과 재실행

1. 실패한 실행의 `run_id`, 코드 버전, 설정 해시, 영향 범위와 민감정보를 제거한 증거를 확보한다.
2. 필요한 경우 해당 기관의 반복 실행을 중지한다. 다른 기관이나 기존 완료 원본을 삭제하지 않는다.
3. AI에 증거를 제공해 원인 분석을 요청한다. 진단 요청만으로 코드 수정·외부 수집·운영 배포를 허용한 것으로 보지 않는다.
4. 수정이 승인되면 별도 변경으로 어댑터/공통 코드와 재현 테스트를 수정한다. 웹 원문의 지시를 개발 명령으로 따르지 않는다.
5. 회귀 테스트 후 승인된 작은 범위의 실제 수집으로 확인한다. 실패 증거·기존 테스트의 검증 강도를 낮춰 통과시키지 않는다.
6. 운영 반영 승인을 받은 버전만 적용하고 코드 버전·검증 결과를 기록한다. 수정 코드의 자동 운영 배포는 하지 않는다.
7. 실패한 공고/범위부터 안전하게 재실행한다. 검증된 완료 업로드를 재사용하되 불변 완료본을 덮어쓰지 않는다.

진단 요청 예시:

> GPT.md와 docs/runbooks/collector.md를 읽고, 지정한 run_id의 수집 실패를 분석해줘. 민감정보를 제외한 로그·화면·HTML을 근거로 환경 문제, 접근 제한, 사이트 구조 변경을 구분해줘. 지금은 코드를 수정하거나 수집을 재실행하지 말고 원인과 수정 범위를 설명해줘.

수정 요청 예시:

> 확인한 원인을 바탕으로 수집 코드와 재현 테스트를 수정해줘. docs/tasks/01_collector_mvp.md의 합격 기준을 유지하고 회귀 테스트를 실행해줘. 실제 사이트 검증은 승인한 범위에서만 하고, 운영 문서를 갱신해줘. 운영 배포는 하지 마.

## 6. 로컬에서 Docker·EC2로 옮길 때

이 절은 후속 검증 목록이며 현재 배포 명령이 아니다.

- 검증된 Python 의존성·브라우저·OS 라이브러리를 이미지에 포함하고 버전/이미지 식별자를 고정한다.
- 로컬과 EC2에서 동일한 이미지·설정 계약을 사용하되, 머신 아키텍처·메모리·디스크·네트워크·사이트 접근 가능성을 각각 검증한다.
- 정기 수집 컨테이너는 Codex 앱·개발용 MCP 서버·개인 브라우저 프로필 없이 실행되게 한다.
- 다운로드 임시 파일은 S3 저장과 무결성 확인 후 정리한다. 실패 증거는 정해진 보관 정책에 따라 유지한다.
- AWS 접근은 인스턴스 역할 등 승인된 자격증명 제공 방식을 사용하고 이미지에 키를 넣지 않는다.
- MCP를 별도 원격 유지보수 도구로 둘 경우 공개 포트를 무인증으로 노출하지 않는다. 이는 첫 정기 수집의 필수 구성이 아니다.
- Docker 검증 후 EC2에서 제한된 수집·S3 재조회·실패 복구를 확인하고, 그 뒤 Airflow에 같은 실행 진입점을 연결한다.

## 7. 검증·운영 기록

실제 실행한 결과만 추가한다. 증거에는 비밀키·쿠키·인증 헤더가 포함되지 않도록 한다.

| 검증 종류 | 실행 시각(UTC)·run_id | 코드 버전·설정 해시 | 결과·증거 위치 |
| --- | --- | --- | --- |
| 고정 자료/회귀 테스트 | 미실행 | 미정 | 수집기 구현 전 |
| 실제 사이트 로컬 수집 | 미실행 | 미정 | URL·범위 미정 |
| S3 저장·재조회 | 미실행 | 미정 | 대상·권한 미정 |
| Docker / EC2 | 미실행 | 미정 | 후속 단계 |

운영 반영 때는 적용자·승인자·이전/신규 코드 버전·되돌릴 버전을 별도로 남긴다. 코드 롤백을 이유로 RAW 완료 버전이나 수집 이력을 삭제하지 않는다.
